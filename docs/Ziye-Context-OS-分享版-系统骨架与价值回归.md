# Ziye Context OS：不是笔记库，是给 AI 用的个人上下文操作系统

## 先说结论

我做这套系统，不是为了把资料分很多文件夹，也不是为了让 AI “记住更多”。

它解决的是一个更具体的问题：**一个人长期做项目、换工具、换模型、换设备后，判断、进度、经验和真实状态会不断断裂。**

所以我把这些东西从聊天记录和脑子里拆出来，变成 AI 可读取、可调用、可更新、可复盘的资产。任何新的 AI 工具进入后，不需要从零问我“你是谁、你在做什么、你喜欢什么风格”，而是先按规则读取正确的层级，再开始工作。

核心公式：

> 上下文不是一次性 Prompt，而是持续更新、按需加载、可验证、能回收的资产系统。

---

# 1. 它解决的不是“存储”，而是四种断裂

| 常见问题 | 传统笔记库的结果 | Context OS 的处理方式 |
|---|---|---|
| Prompt 越积越乱 | 收藏了很多，真正要用时找不到 | 将被验证过的 Prompt 变成可索引资产 |
| 换 AI 工具要重新解释背景 | 每换一次工具，就重新讲身份、项目和偏好 | 用统一入口文件提供身份和行为边界 |
| AI 会话结束就丢上下文 | 重要判断停留在聊天记录里 | 对话结束强制提取价值并路由归档 |
| 文件越来越多但越难用 | 分类细，但没有调用规则和淘汰机制 | 用“价值生命周期”管理资产的进入、索引、归档和删除 |

这里最重要的一点是：**文件不是价值本身。能在未来某个具体场景被调用的判断、能力、关系、证据和产出，才是价值。**

# 2. 系统总架构：入口、状态、判断、协议、资产

```text
┌──────────────────────────────────────────────────────────┐
│ 入口层                                                     │
│ AGENTS.md / CLAUDE.md / INJECT.md                         │
│ 作用：身份、边界、写作风格、AI 工作纪律                    │
└───────────────────────┬──────────────────────────────────┘
                        │ AI 进入时先拿到最小核心上下文
┌───────────────────────▼──────────────────────────────────┐
│ 动态状态层                                                 │
│ chat-worksite.md / NOW.md / focus.md                      │
│ 作用：上次做到哪、现在真实发生什么、此刻优先级是什么        │
└───────────────────────┬──────────────────────────────────┘
                        │ 根据任务类型按需读取
┌───────────────────────▼──────────────────────────────────┐
│ 判断与协议层                                               │
│ JUDGMENT.md / 06-Protocols/                               │
│ 作用：如何做判断、如何执行、如何决策、如何归档、如何维护    │
└───────────────────────┬──────────────────────────────────┘
                        │ 调用对应资产，不全仓扫描
┌───────────────────────▼──────────────────────────────────┐
│ 资产层                                                     │
│ 01-Me ~ 12-Analysis + output / research / tmp             │
│ 作用：身份、项目、知识、洞察、工具、技能、写作、分析等      │
└──────────────────────────────────────────────────────────┘
```

这套结构刻意避免两种极端：

1. **全塞进 System Prompt**：上下文很快过期、长度失控，也无法承载项目细节。
2. **每次从整个仓库检索**：慢、噪音大，而且 AI 容易把无关文件当成当前事实。

正确做法是：入口文件只提供“我是谁、哪些事不能做、如何开始”；真正的任务先读动态状态，再路由到对应资产层。

# 3. 文件夹体系：每一层只回答一种问题

```text
Context-OS/
├── 01-Me/              # 我是谁：原则、约束、身份、偏好、私密信息隔离
├── 02-Network/          # 我认识谁：合作方、人脉、可调用资源
├── 03-Current/          # 我现在在做什么：焦点、计划、对话现场、阻塞项
├── 04-Projects/         # 我正在推进什么：每个项目的真实状态、证据、里程碑
├── 05-Prompts/          # 哪些提示词已经被验证可以复用
├── 06-Protocols/        # AI 和系统该如何工作：读取、执行、决策、归档、维护
├── 07-Knowledge/        # 哪些领域知识未来会在多个项目复用
├── 08-Insights/         # 哪些已验证的判断会改变决策或自我认知
├── 09-Tools/            # 哪些工具和脚本真实节省过时间，失败时怎么回退
├── 10-Skills/           # 哪些能力可以被外部验证并交付成果
├── 11-Write/            # 哪些写作是可复用的表达资产
├── 12-Analysis/         # 决策过程、复盘、研究和推理链
├── output/              # 给外部的人看的最终交付物
├── research/            # 研究中的中间成果
└── tmp/                 # 一次性草稿与临时文件，定期清理
```

## 每层的职责边界

| 层 | 存什么 | 不该存什么 | 典型用途 |
|---|---|---|---|
| 01-Me | 经过验证的原则、不可碰的边界、稳定偏好 | 临时情绪、未经验证的念头 | 防止 AI 用错误的方式帮助你 |
| 02-Network | 有真实关系、能力可定位、能在具体问题上调用的人 | 只看过主页的陌生人 | 需要咨询、合作、求证时找到正确的人 |
| 03-Current | 今天/本周的现实状态、工作现场、阻塞项 | 长期知识、项目历史全文 | 防止 AI 按过期状态给建议 |
| 04-Projects | 有明确交付、真实进度、可验证证据的项目 | 只有想法的脑暴 | 让 AI 按项目真实边界推进 |
| 05-Prompts | 至少复用过、效果稳定的 Prompt | 一次性调试 Prompt | 跨项目、跨工具复用工作方法 |
| 06-Protocols | 为防止真实错误而产生、被重复调用的规则 | 纯理论流程 | 把“知道”变成“每次都会做” |
| 07-Knowledge | 未来至少三个项目可能复用的领域理解 | 随手可搜的常识 | 技术/行业问题的长期积累 |
| 08-Insights | 能改变决策、产品方向或自我认知的已验证判断 | 情绪碎片、未经验证的直觉 | 防止重复踩同一种坑 |
| 09-Tools | 实际用过、能节约时间、包含回退方案的工具经验 | 只安装未使用的软件 | 提升执行效率，避免重复试错 |
| 10-Skills | 可外部验证、能交付、有作品支撑的能力 | “我想学”的愿望 | 简历、分工、能力缺口识别 |
| 11-Write | 可以引用、改写、发布的成熟表达 | 未整理草稿 | 保持跨场景表达一致 |
| 12-Analysis | 有推理链、可事后复盘的研究与决策 | 只有结论的事后合理化 | 重要决策可追溯、可修正 |

# 4. AI 的读取逻辑：不是“读得越多越聪明”

## 最小读取集

任何非微任务开始前，AI 必须先读三类动态信息：

```text
1. 上一次做到哪里：chat-worksite.md
2. 当前真实主线与冲突：NOW.md
3. 当前优先级与时间边界：focus.md
```

然后才按任务路由：

| 用户要做什么 | AI 还应该读什么 |
|---|---|
| 做项目或技术方案 | 对应项目的 PROJECT.md 和技术文档 |
| 做重大决策 | 判断引擎、原则、约束、决策协议 |
| 写文案、文章、回复 | 写作风格和同类代表作 |
| 安排今天/本周 | 当前计划、活跃项目、人脉行动板 |
| 处理合作与关系 | 人脉档案、约束、判断框架 |
| 学一个技术或使用工具 | 知识层、工具层、对应项目档案 |

## 为什么这样做

- **状态文件解决“现实是否已经变化”**。项目档案可能记录完整，但今天优先级可能已经变了。
- **任务层解决“别编造项目细节”**。没有读项目档案，就不能假装知道项目的真实实现。
- **协议层解决“别靠模型临场发挥”**。关键动作要有固定规则，尤其是决策、归档和隐私处理。

一句话：**先看现在，再看任务，再调用历史。**

# 5. 真正的核心：价值回归机制

目录分类只能解决“放在哪”。一套系统能长期有效，靠的是回答“什么值得留下、留下后如何继续产生价值”。

## 价值判断标准

每个资产进入系统前，都要回答：

> 未来哪个具体场景会用到它？

如果回答不出来，它大概率只是噪音，不该进入正式层。

例如：

- 一条原则，至少要在两次真实决策中被验证过，才能进入 `principles.md`。
- 一个项目，必须有明确交付、真实进度和可验证证据，才能进入 `04-Projects/`。
- 一个 Prompt，至少跨场景用过两次且效果稳定，才进入 `05-Prompts/`。
- 一条洞察，必须能改变一个决策、产品方向或自我认知，才能进入 `08-Insights/`。
- 一个技能，必须有代表作和外部可验证的交付，不能把“想学”写成“会”。

## 价值生命周期

```text
阶段 0：临时价值点
  对话中刚出现，尚未验证，先放进工作现场
          ↓
阶段 1：验证价值点
  被实际使用一次 / 有证据支持 / 被明确确认
          ↓
阶段 2：固化资产
  写进唯一的正式位置，避免多处复制
          ↓
阶段 3：索引化
  被高频引用后，进入该层 index，成为默认入口
          ↓
阶段 4：归档或删除
  项目结束、长期未引用、被替代、重复或无法验证
```

这条链路的意义不是“整理得更漂亮”，而是让经验从一次对话里留下来，经过验证后变成未来能节省时间、提高判断质量的东西。

# 6. 对话结束不是结束，而是资产入库

普通 AI 对话的问题是：聊完就散。Context OS 把收尾固定成四步。

## Step 1：提取价值点

每次实质对话结束，明确列出是否产生了：

- 决策：决定了什么，依据是什么。
- 教训：哪里出错，下次怎么避免。
- 知识：修正了什么技术或行业认知。
- 人脉：谁可以在什么问题上被调用。
- 方法：出现了什么可复用流程或代码配置。
- Prompt：是否值得变成模板。
- 洞察：是否改变了产品、技术或自我理解。

不接受“今天讨论了项目”这种废话。要写成“某个方案被否决，因为真实用户流程中缺少可验证收益”。

## Step 2：为价值找唯一落点

| 价值类型 | 归档位置 |
|---|---|
| 项目方案、真实进展、项目卡点 | 04-Projects/对应项目 |
| 原则与红线 | 01-Me/ |
| 可复用知识 | 07-Knowledge/ |
| 已验证洞察 | 08-Insights/ |
| 工具经验 | 09-Tools/ |
| 最终写作成果 | 11-Write/ |
| 决策过程与复盘 | 12-Analysis/ |
| 对外交付物 | output/ |
| 私密信息 | private/，不进入公开分享包 |

## Step 3：执行归档

优先更新已有文件，不随手新建重复文档；重要项目文件或系统原则发生变化时，要先展示 diff，再确认修改。

## Step 4：更新工作现场

记录本轮完成、未确认问题和下次第一步，保证新会话不会断档。

# 7. 决策不是“我觉得”，而是可回滚的推理链

Context OS 里，重要决策不允许只写结论。至少要留下：

1. 问题到底是什么。
2. 有哪些选项，包括“不做”。
3. 每个选项的时间、金钱、精力和机会成本。
4. 每个选项的短期收益、长期收益和战略价值。
5. 风险、概率、影响、是否可恢复。
6. 当前的信息缺口。
7. 推荐方案。
8. 为什么是现在。
9. 失败时的触发条件和回滚动作。

这不是为了把决策写得形式化，而是防止三类错误：

- 把一时情绪当判断。
- 因为一条新信息就推翻整个项目。
- 把不能回滚的重投入当成“勇敢”。

原则很简单：**新信息只修改它真正证伪的那个假设；其他部分默认不动。**

# 8. 隐私不是补丁，而是系统设计的一部分

如果一个个人 Context OS 无法分享、无法协作，通常不是它不够完整，而是没有先做好隔离。

我把信息分成三类：

| 类别 | 内容 | 分享规则 |
|---|---|---|
| 公共方法论 | 目录结构、协议、通用模板、价值管理规则 | 可以直接分享 |
| 工作资产 | 项目框架、研究方法、可公开作品 | 经过项目级脱敏后分享 |
| 私密资产 | 联系方式、账号、家庭信息、未公开合作、情绪原文、凭证 | 永不进入公开仓库或分享包 |

所以分享给朋友时，不应该把个人仓库直接压缩发过去。正确做法是：

1. 只分享公共骨架和示例模板。
2. 用虚构示例替换真实人名、公司、项目、日程和联系方式。
3. 私密目录不纳入版本控制，也不进入导出包。
4. 输出前做一次敏感信息扫描：密钥、手机号、邮箱、住址、身份信息、未公开合作方、内部财务等。

# 9. 给朋友的最小可用版本：不要一上来建 12 层

完整系统是从真实项目里长出来的，不适合第一天照抄全部结构。

## 个人版 MVP

先建 6 个目录和 4 个入口文件就够了：

```text
My-Context-OS/
├── AGENTS.md            # 给 AI 的入口说明
├── NOW.md               # 当前真实状态
├── SOUL.md              # 长期身份、偏好和边界
├── README.md            # 系统说明与目录索引
├── 01-Me/               # 原则、约束、私密信息隔离
├── 03-Current/          # 今天/本周/对话现场
├── 04-Projects/         # 每个活跃项目一张 PROJECT.md
├── 06-Protocols/        # 先有读取、执行、归档三个协议
├── 07-Knowledge/        # 只放跨项目复用的知识
└── 12-Analysis/         # 决策和复盘
```

## 先写四个文件

### `SOUL.md`

回答：

- 我是谁。
- 我长期想做什么。
- 我的表达风格是什么。
- AI 绝不能替我做什么。

### `NOW.md`

回答：

- 现在最重要的 1–3 件事。
- 哪些项目暂停。
- 哪些现实约束正在影响判断。
- 最近发生了什么，会改变 AI 的建议。

### `04-Projects/项目名/PROJECT.md`

每个活跃项目只需要先写：

```markdown
# 项目名

## 解决什么具体问题

## 当前阶段

## 已验证事实

## 未验证假设

## 本周唯一目标

## 当前 blocker

## 下一步可见证据
```

### `06-Protocols/context-loading.md`

把 AI 的第一条工作纪律写清楚：

```markdown
每次非微任务开始前：
1. 读取 NOW.md；
2. 读取 03-Current/；
3. 读取任务对应的 PROJECT.md 或知识文件；
4. 明确区分事实、判断和待确认问题；
5. 不读到的内容不假装知道。
```

## 三条必须先跑通的协议

1. **读取协议**：AI 每次先读什么，才能不按过期状态做事。
2. **执行协议**：修改前说明影响范围，修改后提供可验证结果，保持可回滚。
3. **归档协议**：一次实质对话结束后，把有价值的内容放到唯一正确的位置。

先稳定运行两周，再考虑增加人脉、Prompt、技能和洞察层。目录不是越多越好，只有被反复调用的结构才值得保留。

# 10. 朋友可以直接照抄的 AI 工作提示词

```text
你正在协助我维护一个个人 Context OS。

工作规则：
1. 非微任务开始前，先读取 NOW.md、03-Current/ 和本任务对应的项目/知识文件。
2. 不要全仓扫描；按任务路由读取，读不到的信息明确说明缺口。
3. 先给结论，再给依据和下一步；区分已知事实、你的判断、需要我确认的内容。
4. 不要把个人隐私、凭证、联系方式和未公开合作信息写进可公开文件。
5. 做重要决策时，必须同时列出选项、成本、收益、风险、信息缺口和回滚条件。
6. 对话结束后，提取可复用的决策、知识、教训或方法，并归档到唯一正确的位置。
7. 不为了“整理”制造新文件；每个文件都要能回答未来会在哪个具体场景被调用。
```

# 11. 这套系统的边界

它不是第二个 Notion，不是自动记录一切，更不是让 AI 替人做人生和商业决策。

它的边界很明确：

- AI 可以整理、检索、提出风险、给出方案。
- AI 不能编造进度，不能把猜测写成事实。
- AI 不能代替人做不可逆的关系、商业或人生决定。
- 系统不追求“记录完整”，追求“在关键时刻能调出正确的上下文”。
- 任何资产都必须能被未来调用；不能调用的东西宁可留在临时区，也不要污染主系统。

---

# 12. 一句话总结

> 个人 Context OS 的本质，不是把人生装进文件夹；而是把会反复影响判断和行动的东西，变成 AI 能正确读取、持续验证、长期复用的资产。

如果只记住三件事：

1. **入口注入身份，动态文件记录现实，任务文件承载细节。**
2. **任何信息都要问：未来在什么具体场景会被调用。**
3. **每次对话都要把价值从聊天里拉回系统里。**
