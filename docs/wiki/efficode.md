## 一、语言结构

**符号化指令集 + 前缀表达式**。六条指令, 二进制里各一个 opcode:

| 符号 | opcode | 载荷 | 语义 |
|---|---|---|---|
| `@DID:` | 1 | 有 | 身份 (发送方身份串) |
| `#DATA:` | 2 | 有 | 数据正文 |
| `#REQ:` | 3 | 有 | 请求 |
| `!ACK` | 4 | 无 | 确认 |
| `!SEND` | 5 | 无 | 发送 |
| `!END` | 6 | 无 | 结束 |

指令段二进制形状逐条: `[1B opcode][varint payloadLen][payload UTF-8]` —— **末尾没有隐式终止符**,
靠 `payloadLen` 自描述; 少一个字节就报截断。不在表里的 opcode 一律抛 `EFFICODE_UNKNOWN_OPCODE`
(变异 M1 就是把这里改成"宽容跳过", 门当场变红 —— 这条断言存在的意义就是这个)。

**前缀表达式文本形态**是 `instructionsToSymbolic()` 的产物, 例 (门 [C] 真跑出来的):

```text
@DID:did:bolloon:a #DATA: !SEND
```

`symbolicToInstructions()` 的解析规则是**写死的四条**, 不是"随便切":
① 按空白切词; ② 词首是 sigil (`@` / `#` / `!`) 必须匹配一条**已知**前缀, 否则抛;
③ 不带 sigil 的词追加到**上一条**指令的载荷后面 (没有上一条 → 抛);
④ 控制指令 (`!ACK`/`!SEND`/`!END`) 后面不许跟载荷。

**双模式**: `compact` (默认, 真二进制) 与 `text` (整包 Base64 → 线上是可打印文本)。
包头低 4 位记 mode; 解析时**传输形态与包头声明不一致即抛** `EFFICODE_BAD_MODE`
(把 Base64 串当二进制喂进去就会红 —— 门 [B] 有一条专门测这个)。

**三条协商硬规则** (`negotiate.ts`, 落地在 `encodeForPeer`/`decodeFromPeer`):
① 只有**双方都声明** `efficode` 才用 Efficode;
② 单方声明 / 对端不支持 / 对端声明了本机不认识的字符串 ⇒ **明确回落自然语言**, 并**记一笔**;
③ 声明语言**不是** efficode 的载荷, **绝不去解析它** (不猜、不试解) —— 对端声明 `efficode` 而本机没声明支持时抛 `EFFICODE_LANG_UNSUPPORTED`, **不硬解**。
本机默认声明**永不猜成 efficode**: 没给就是 `natural` (env 可覆盖: `BOLLOON_EFFICODE_LANG`)。

## 二、包结构

```text
[Header 2B] | [DID 验证段 32B (可选)] | [指令段 动态] | [数据块 动态] | [CRC32 4B]
```

**Header 2B**:

| 字节 | 位 | 含义 |
|---|---|---|
| byte0 | 高 4 位 | 版本 (`EFFICODE_VERSION = 1`) —— 不认识就抛 `EFFICODE_BAD_VERSION` |
| byte0 | 低 4 位 | 模式 `0=compact` · `1=text` |
| byte1 | bit0 | 有 DID 段 |
| byte1 | bit1 | 有指令段 (**本实现必置 1** —— 不接受无指令的包) |
| byte1 | bit2 | 有数据块 |
| byte1 | bit3 | 数据块已压缩 |
| byte1 | bit4..7 | 保留, **必须 0** (置位即抛 `EFFICODE_BAD_FLAGS`) |

**指令段**: `[varint opLen][opBytes]` · **数据块**: `[varint dataLen][dataBytes]`,
其中 `dataBytes[0]` = 压缩算法 id (`0=none` `1=lz77` `2=deflate`), 未知 id 抛 `EFFICODE_UNKNOWN_COMPRESSION`。

**两处"诚实边界"写在包层**:

- DID 段 32B 在规范里是**固定段**, 参考实现**允许省略** (省 32B), 省略时 flags 如实写 0,
  解码端**按 flags 解、不假设段存在**。所以 `MIN_PACKET_BYTES = 2 + 1 + 2 + 4 = 9B` 是"无 DID 段"的下限,
  带 DID 段的包应 ≥ 41B —— 由 flags 驱动逐段校验, 不靠这个下限兜。
- **CRC32 只防传输损坏, 不是防篡改** (无密钥)。篡改要真签名 —— **规范中**, 见 §三。

**两条硬纪律** (变异 M1/M2 就是拆这两条, 门必须变红): ① 解析必须**逐段自描述**, 长度对不上就报截断;
② 尾段 CRC32 覆盖 CRC 之前的**全部**字节, 对不上就报 `EFFICODE_CRC_MISMATCH`, 绝不放行"内容看着像就收下"。
匿名自证: `crc32("123456789") === 0xCBF43926` (规范向量, 门里真跑)。
门 [B] 还把包**截断到任意长度 (122 种)**逐种试解, 要求泄漏 = 0。

## 三、身份与安全

**DID 段 32 字节布局** (`did.ts`):

| 偏移 | 长度 | 内容 |
|---|---|---|
| 0 | 1B | algo id (= 1, `sha256-截断`) |
| 1..3 | 3B | 原始身份串字节数 (24 位大端, 上限 16MB) |
| 4..31 | 28B | `sha256(身份串)` 的**前 28 字节** |

**真做了的**: 编/解段 · 摘要比对 (`matchesDidSegment`, 返回值如实标 `method: 'digest'`、`signed: false`) ·
摘要的稳定文本形式 `algo1:<56 hex>` (单向, 可安全落日志) · 未知 algo id 抛 `EFFICODE_DID_SEGMENT_BAD`。

**明确没做的 (不许含糊)**:

- 32B **装不下**一个 DID / 公钥 ⇒ 本段是**摘要**, 只能做"是不是同一个身份"的比对,
  **不能**从段里还原身份, 也**不能**独立证明持有私钥。门里有一条专门验"摘要里不含原文"。
- **链上签名验证** / **ECC 临时会话密钥** = **规范中, 未实现**。本模块**没有**签名函数,
  也**没有**密钥交换函数 —— 刻意不写假实现。签名校验的接线点在 packet 层的 `verifyDid` 回调(预留),
  现成能用的只有摘要比对这一条。
- CRC32 **不做认证** (§二)。所以今天这条链的**真实性保护是 0**: 有能力改包的人可以改完重算 CRC。

**协商本身也是安全口的一部分**: 对端声明了本机不认识的语言时, 载荷**原样呈现、绝不进解码器**
(门 [C] 两条断言 + 变异 M4 拆掉它必红); 对端声明 `efficode` 而本机没声明支持时**拒解**。
换句话说"猜着解"在三个地方被堵死: 未知 opcode、未知压缩 id、未知语言声明。

## 六、"更高效吗" —— 诚实回答

### 6.1 宣传句 vs 实测 (同一样本, 真跑)

| leo 原稿的说法 | 我实测到的 | 判据出处 |

| 「压缩率提升 30%」 | **逐样本差极大, 没有单一数字**: 12B 寒暄包/自然帧 = **-31.8%** · 51B 群消息 **-25.3%** · 77B 任务公告 **-28.5%** · 1KB 重复日志 **-76.7%** · 真发 JSON 帧 x40 **-92.9%** · 半可压十六进制 1KB **-58.0%**(对正文) · **真随机 1KB: 负收益** (lz77 **+13.0%**, deflate +0.6%) | 门 [D] 逐样本 + `pickAlgo` 在不可压内容上真退回 `none` |
| 「信息密度提升 20 倍」 | **实测最高 14.15x** (真发 JSON 帧 x40: 4089B → 289B); 12B 寒暄只有 **1.47x** | 同上 |
| 「兼容度 100%」 | **未测** —— 只有本仓**一个**实现, 没有第二实现互编互解 | 无 |
| 「微秒级」 | **未测** —— 没有任何编解码耗时基准 | 无 |
| 「链路缩短 50%」 | **未测** —— 没有端到端延迟测量 (字节数 ≠ 链路时间) | 无 |
| 「物理定律级」 | **不作判据** —— 不可证伪的表述, 不进验收表 | — |

> 一句话: **"省"是真事, 但省的倍数完全取决于内容, 而且短消息上是负的** —— 见 6.2。

### 6.2 最要紧的一条: **短消息会被包头吃回去**

用 20 字节载荷 (20B ASCII) 真编真解, 逐段拆开 (`@DID:` 指令把身份明文再写一遍 = 今天 `encodeForPeer` 的真实路径):

```text
载荷 = 20B
[带 DID 段] 3 指令无压缩包   = 111B     ← 实测
  算式: 2(Header) + 32(DID段) + 1(指令段长 varint)
      + 50(指令段: @DID: 1B码+1B长+44B身份明文 / #DATA: 2B / !SEND 2B)
      + 1(数据块长 varint) + 1(压缩算法id) + 20(载荷) + 4(CRC32) = 111B  ✅ 算式 == 实测

  净开销 = 111 - 20 = 91B
  开销/载荷 = 91 / 20 = 4.55x
  总/载荷   = 111 / 20 = 5.55x
```

同一条载荷的对照:

| 口径 | 包总字节 | 净开销 | 开销/载荷 | 总/载荷 |
|---|---|---|---|---|
| 今天 `encodeForPeer` 真实路径 (身份写两遍: 32B 摘要段 + `@DID:` 44B 明文) | **111B** | **91B** | **4.55x** | **5.55x** |
| 去重口径 (身份只留 32B 摘要段, 不重复 `@DID:` 指令) | **33B** | **13B** | 0.65x | 1.65x |
| `text` 模式上线 (整包 Base64) | **148 字符** | — | — | ×1.354 (Base64 膨胀) |
| 自然语言帧基线 (真代码: `buildAgentMessage(无声明).frame`) | 159B | — | — | — |

**固定开销不随载荷消失** (带 DID 段 · 3 指令 · 无压缩, 真跑):

| 载荷 | 包 | 净开销 | 开销/载荷 |
|---|---|---|---|
| 0B | 89B | 89B | 纯开销 |
| 12B | 103B | 91B | 7.58x |
| 20B | 111B | 91B | 4.55x |
| 50B | 141B | 91B | 1.82x |
| 100B | 191B | 91B | 0.91x |
| 1KB | 1116B | 92B | 0.09x |
| 4KB | 4188B | 92B | 0.02x |
| 16KB | 16477B | 93B | 0.006x |

三条由此**量出来**的结论:

1. **短消息上包比正文大得多**: 20B → 111B (**放大 5.55x**)。开销要到载荷 ~100B 才降到 1x 以下,
   ~4KB 才基本可忽略 (1.02x)。所以 Efficode **只在大而重复的结构化文本上真省**。
2. **身份被写了两遍**, 白白多花 46B (`@DID:` 的 1B 码 + 1B 长 + 44B 明文), 而包头里已经有 32B 摘要段了。
   这是**已量化的一条设计缺陷候选** (修正属**规范中**, 本轮未改代码)。去掉它, 20B 载荷的包从 111B → 33B。
3. **< 32B 的数据块连压缩头都不开**: `pickAlgo` 直接返回 `none` (省下的不该是负数),
   但数据块仍要多付 1B 算法 id + 1B 长度。强制 deflate 在 20B 上确实更小 (块体 5B ⇒ 包 96B),
   **默认策略仍按"压不小就不压"走**, 不为了好看而硬压。

### 6.3 那什么时候真赚

门 [D] 的真发 JSON 帧样本 (x40, 3350B 正文): 自然语言帧 **4089B** → 紧凑包 **289B** (**省 92.9%**, deflate)。
1KB 重复日志: 804B → 187B (省 76.7%)。**这就是 Efficode 的真正适用面**: 大而重复的结构化文本 / 批量帧。
反过来, 随机字节 / 已高度压缩的内容 / 十几字节的寒暄, 一概不赚甚至倒亏 —— 默认策略会**如实退回 `none`**,
不会为了好看而让包白白膨胀。

## 七、没做到 / 未验证 (逐条, 不许美化)

1. **签名与密钥交换完全没做** —— 没有签名函数、没有 ECC 临时会话密钥、没有密钥轮转;
   今天链上真实性保护 = **0** (CRC32 无密钥, 不做认证)。
2. **声波/语音模式没有一行代码** —— 只有"显式拒绝"这一半。
3. **5G / 区块链适配是纯设想** —— 仓内 0 行代码, 没有上链编码器, 与链上模块零 import 关系。
4. **「兼容度 100%」测不了** —— 只有本仓一个实现, 没有第三方实现对编。
5. **耗时/延迟一个数都没测** —— 「微秒级」「链路缩短 50%」目前**没有判据**。
6. **真跨机未验** —— 门 [E] 的"两个进程"是**同一台机器**走管道; 公网 / 跨设备未做。
7. **短消息开销缺陷未修** —— 身份写两遍 (46B) 已量化, 修正属规范阶段, 本轮**只量不改**。
8. **论坛地址未定** —— leo 原稿提到但没有给地址, 本页不编, 也没有登记任何 raw 来源。
9. **指令集只有 6 条, 没有扩展机制** —— 未知 opcode 一律抛 (这是**故意**的严格性), 但也就意味着
   未来加指令**必须**同时改两端, 没有版本协商位。
10. **客户端 Skills 条目只到"能看见"** —— 手机端点进去给的是名字/一句话/状态/指向本页,
    **不是**可执行的 Efficode 调试器。
