# Agent Event Network — 计划 (不是"去中心化群聊")

## 0. 定位

leo 的目标重新定义为:

> **让 10,000+ 智能体参与协作的去中心化 Agent Communication + Memory 网络。**
> OrbitDB 负责**可验证的共享事件记录与状态同步**; 每个 Agent **本地只保留自己需要的状态**, 历史按需取回。

**群聊只是这个网络的一种 UI**, 不是本体。因此本计划**先不做聊天界面**。

## 1. 现状基线 (逐条对着仓里真代码)

### 1.3 方案判断偏保守的一处

方案把"1 万 Agent 不能进同一个 gossip 网络"当作主要工作量。**分片其实已经天然存在** —— 一群 = 一个独立的 OrbitDB store (一群一地址), 不存在"全网一个大群"。

⇒ 真正要解决的不是"怎么分片", 而是 **A(权限) · B(复制可验) · C(查询) · D(轻量)** 四件。

### 1.4 P0 实测结果 (真两节点, 2026-09-30; 门 `scripts/verify-group-replication.ts`)

**先修一个根因才可能验**: `src/orbitdb/ipfs-node.ts` 的节点**从来没有任何 block broker**
(`createHeliaLight` 不带 bitswap, `withLibp2p` 也不加) ⇒ 新节点按地址打开群的 manifest/oplog 块
**一律拉不到** (报 `No block brokers ... cannot be fetched`) ⇒ 「跨机复制」在修之前**不可能成立**。
修法 = 显式 `withBitswap()` (+ `@helia/bitswap` 进 dependencies)。

| 场景 | 结果 | 数字 |
| --- | --- | --- |
| S1 新节点拿全量 (101 条) | ✓ 通过 | 对端 `seen=101` · 打开 331ms · 拿齐 **5.1s** · 对端磁盘 225.6KB (供块方 198.6KB) · **两侧 oplog 集合指纹逐字相同** |
| S3 反事实 (不拨号) | ✓ 通过 | `seen=0` 且打不开 (A 在线供块 ⇒ 复制确实来自网络) |
| S4 非创建者离线写 | ✓ 通过 | `written=10 ok=true` ⇒ **`write:['*']` 对非创建者真生效** |
| S4 A 重启收敛 (21 条) | ✓ 通过 (A 侧) | A `seen=21` (含 B 离线写的 10 条) |
| **S2 迟到者拿 1001 条** | ✗ **失败** | 等满 **300s 仍 `seen=0`**; C 的**块存储涨到 3.3MB** (比供块方 1.7MB 还大) ⇒ 块在拉, **日志没成形**; 指纹 `e3b0c442…` = 空串 sha256 |
| **S4 B(新进程)回来** | ✗ **失败** | B `seen=0` (A 侧 21) ⇒ 与 S2 同一现象的另一面 |

### 1.6 根因钉死 + S2 转绿 (2026-10-01, 对照实验)

P0b 追到"与条数无关的 ~25-30s 固定停顿"。**决定性对照** (同一件事, 唯一变量是节点配置):

| 节点配置 | 结果 |
| --- | --- |
| 默认 (kadDHT + 两个 delegated-routing 客户端 + autoTLS) | 新节点等 **90343ms** 仍 `seen=0` ✗ 超时 |
| 轻客户端 (`BOLLOON_ORBITDB_LEAN_ROUTING=1`, 只留 pubsub+identify+ping+relay) | 等 **7555ms** `seen=301` ✓ 拿齐 (≈12×) |

⇒ 根因 = **路由服务在拖住块交换**。用轻客户端重跑 P0 四场景:

```
S1 101 条   ✓ 2557ms (原 5136ms)
S2 1001 条  ✓ **27744ms** (原 >300s 超时) ⇒ **P0 的验收项达标**, P0b 的主要症状消失
S3 反事实   ✗ seen=101 —— 门自己的漏洞: 节点默认带 **mDNS**, 同机 peer 不拨号也会被发现
S4 B 侧     ✗ seen=0 (A 侧 21) —— 待单独探 (与 S3 不同因)
```

**代价 (必须写清)**: 关掉 DHT/delegated routing 后**没有全局发现** —— 对端要靠邀请链接里的 multiaddr
直接拨号 (群成员场景够用); 全局发现需要另加一层 (relay/rendezvous 或注册表), 不在本轮。

### 1.7 P1 / P2 已落地 (2026-10-01)

- **P1 DID 门控**: 成员 = DID(Ed25519) 与 OrbitDB 写身份**显式绑定**; 成员变更 = **双侧签名**事件;
  真两节点门 **19/19** (非成员写入被 OrbitDB 自己拒 + 阳性对照 growBy=2 + 三种篡改全部验签失败)。
  **能力边界**: IPFS 型 AC 白名单**不能就地改** (write 在内容寻址的 ACL manifest 里 ⇒ 改名单必然换地址)
  ⇒ 成员变更 = **重建 store + 重新分发链接**; 代价 = 老链接作废 / 历史不自动搬 / 老 store 不回收 /
  **没有双写窗口**。默认**尚未翻成门控** (createGroup 不给 gate 仍是 `write:['*']`, 含本页 P0 分片模块的 4 处)。
- **P2 事件外壳 + 索引**: 统一信封 (10 种 type) + by-topic/capability/time 三个索引;
  真删索引 store 目录后由事件流重放 ⇒ **dag-cbor 字节 + sha256 + canonical JSON 三道逐字节相同** (门 **29/29**)。
  实测修正一条假设: **OrbitDB store 地址 = manifest 参数(含 store 名)的哈希, 与身份/dataDir 无关**。
- 两个门都由主线**独立重跑**过 (不信子智能体自述): P1 19/19 · P2 29/29 · 聚焦单测 63/63 · tsc 0 错。

### 1.5 P0b 实测: 长历史为什么完不成 (2026-09-30, 诊断探针)

探针 (子进程 `probe_sync` 相位: dial → 打开 → 每 5s 报「日志长度 / pubsub 订阅者 / 磁盘」), A 发 301 条并常驻:

```
t= 0s   日志=0    订阅者=1   磁盘=10KB
t= 5s   日志=0    订阅者=1   磁盘=207KB
  ...    日志恒为 0 (磁盘一路涨到 ~1.9MB ⇒ 块确实在拉)
t=65s   日志=301  订阅者=0   磁盘=1766KB     ← 一次到位
打开=70124ms
```

**机制**: `@orbitdb/core` 4.0.0 的 log 在打开时从 heads 起**遍历整条 DAG** 逐块取
(`src/oplog/log.js:272` `Promise.all(getEntries)` + 迭代器), 而**日志要到遍历结束才成形** ——
所以中途 `all()` 恒为 0, 看起来像"卡住", 实际是 70 秒后一次性出现。
⇒ **每开一次群 = O(N) 次取块**: 301 条 70s; 1001 条在 300s 窗口里完不成 (S2 就是这样卡住的)。
⇒ **1 万 agent 规模下这条路不可用**, 正解 = **快照 + 尾巴**: 定期把日志状态压成一份快照,
新节点只取「1 份快照 + 尾部增量」, 不必重走全 DAG。这与 P3「轻量化」是同一套机制。

**结论**: 小历史 (101 条) 的真两节点复制**成立且可复现**; **长历史 (≈1000 条) 的 log 同步完不成** ——
修法已定见 §1.5 (**快照 + 尾巴**), 未实现。**在 S2 通过之前, 「1 万 agent 拿历史」这一条不许算数。**

## 2. 核心命题 (可测, 不是口号)

> 当 Agent 数量从 100 涨到 10,000 (**×100**) 时, **单个 Agent 的本地占用 / 事件带宽 / 查询延迟**
> 必须近似 **O(1) 或 O(log N)**, 不允许 O(N)。

四个可量化的量 (每个都要真跑数字, 不许估):

1. 本地磁盘占用 / agent (目标: 与"我加入多少群"近似正比, 与**全网** agent 数无关)
2. 事件带宽 / agent / 分钟 (与订阅的 topic 数相关, 与全网事件率**无关**)
3. 查询延迟 P50/P95 (目标 <1s @ 结构化索引)
4. 迟到者拿到 N 条历史的耗时与字节

## 3. 待 leo 拍板的三个决定 (会改变架构)

| # | 问题 | 我的建议 |
| --- | --- | --- |
| Q1 | "1 万智能体" = 1 万个**独立节点**, 还是 1 万个**身份**跑在少数节点? | 先按 **身份数** 设计(1 节点多身份), 但**每身份独立密钥 + 独立订阅集**; 节点数后置 |

| Q3 | "可被调用" = 可检索, 还是"可执行群聊"(事件即委托 → 真执行 → 结算)? | 两者分阶段: 先**可检索可复现**, 后接委托执行(零件已有: task 协议 + delegate + x402) |

## 4. 执行路径 (每阶段都有自己的判据门; 没有门不算做完)

### P0 · 真两节点复制基线 (最关键, 也是唯一完全没验过的)
**做什么**: 起两个真 OrbitDB 节点 (不同端口/不同 HOME) → A 建群发 N 条事件 → B 用 `orbitdb://<addr>?type=group&name=…` 加入 → **真拿到**这些历史。
**门 `scripts/verify-group-replication.ts`** (真进程, 不许 fake):
- N=100 条: B 到达"看见 100 条"的耗时 / 传输字节 / 双方磁盘增量
- N=1000 条: 同上 + 单条重放开销 (是否随历史线性退化)
- 反事实: 不加入的节点**必须看不见** (否则门是假绿)
- 断网 30s → 双方各发 10 条 → 重连 → **两侧收敛到同一 oplog 顺序**(逐条比对)
**产出**: 一张真数字表 (这决定后面所有设计)。

### P1 · 写权限: `write:'*'` → DID 门控
**做什么**: 群 accessController 从 `write:'*'` 改为按成员 DID 白名单 (或自定义 controller); 邀请加入 = 把 DID 加进白名单的事件。
**门**: ① 非成员节点写入**必须被拒**(真两节点) ② 成员写入照常 ③ 白名单变更本身是一条可验签事件 ④ 反向: 白名单移除后**新**写入被拒、旧历史仍可读。

### P2 · 事件统一 + 索引层
**做什么**: 把 message / delegation / proposal / result / payment / discovery 统一成一种 event 外壳 (`{id, type, actor, group, ts, refs, summary, cid}`), 事件本体只放**元数据 + CID**; 建三个索引 store: `by-topic` · `by-capability` · `by-time` (keyvalue, 天然可增量复制)。
**门**: ① 同一语义事件跨库字段一致 ② 索引可由事件流**重建**(删掉索引 → 重放 → 逐字节相同) ③ 老记录向后兼容可读。

### P3 · 轻量化 + **快照/尾巴** (量化, 不靠感觉)

> 2026-09-30 更新: P0b 证明「每次打开都全量走 DAG」是 O(N) ⇒ P3 的第一件事是**快照 + 尾巴**
> (定期压实日志 + 新节点只取快照与增量), 之后才是保留口径与裁剪。两件事共用同一套机制。
**做什么**: 大内容只出 CID (share 按需) + 保留口径 (最近 N / 我参与的) + 可选裁剪。
**门**: 同一台机器上, 从 1 群 → 10 群 → 100 群(同一事件量), 量"本地占用/agent"的曲线; **必须与群数近似正比、与全网 agent 数无关**; 并给出"删掉本地大块后仍能按 CID 取回"的真跑证据。

### P4 · 查询面 (先结构化, 语义后置)
**做什么**: 一个 `query(topic?, capability?, since?, actor?, group?)` 的读口 —— 走 P2 的索引 store, 返回 `{event_id, cid, summary, actor, ts}` 列表 (不返回大内容); 复用 `src/web/server.ts` 与链上索引的既有形状。
**门**: ① 同一查询在**两个不同节点**返回同一集合 (逐条比对) ② 查询**不触发**全量下载 (用字节数证明) ③ 断网时降级为本地索引 + 如实标注"仅本地"。
**不做**: 本轮不上 embedding/语义检索 (判据难做门, 且仓里无 embedding 设施) —— 语义放 P5 之后单独论证。

### P5 · N-agent 规模压测 (100 → 500 → 1000)
**做什么**: 复用仓里既有的真子进程夹具 (`scripts/lib/*-child.ts`) 起 N 个 agent (各自 HOME/端口/身份), 跑"发布事件 → 查询 → 取 CID → 本地执行 → 回写结果"。
**门**: 依次给出 100/500/1000 三档的 §2 四个量, 并**判定 O(·)** —— 若某量随 N 线性增长, 必须**如实写出**并归因, 不许挑好看的档位汇报。

## 5. 明确不做 (本计划边界)

- 不做聊天 UI (先有网络, 再有界面)
- 不做"每节点全量复制"(与目标冲突)
- 不引入中心化索引/SQL (与去中心化冲突; 查询必须能在任一节点独立可答)
- 不重造身份/支付/任务协议 (已有 DID · x402 · 14 态任务协议)
- 不改冻结面 `goal-flywheel/types.ts` 与既有调用方

## 6. 没验的部分 (如实)

- ~~迟到者的历史回填能力未知~~ → **P0 已答一半**: 101 条成立 (5.1s), **1001 条完不成** (300s 超时、块到日志不到) ⇒ 见 §1.4
- 真两节点下的 CRDT 收敛速度与字节成本**未知**(现有测试全是 fake)
- `src/orbitdb/orbitdb-core.d.ts` 只声明了 `keyvalue` 子集, 而实际用法含 `events` + `openStoreByAddress` ⇒ **类型面比用法窄**, 大改前需补齐 (否则 tsc 放行、运行期裸奔)
